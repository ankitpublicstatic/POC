# PART 1️⃣ — Why Netty does NOT allocate one thread per request

## Traditional Model (Spring MVC + Tomcat)

### Thread-per-request model

```
Client ──HTTP──▶ Thread-1 ── DB ──▶ Response
Client ──HTTP──▶ Thread-2 ── API ─▶ Response
Client ──HTTP──▶ Thread-3 ── IO ──▶ Response
```

### What goes wrong at scale

Each request blocks a thread
Threads consume:

  ~1MB stack memory
  CPU context switching
If DB/API is slow → thread is idle but occupied

🧠 10k concurrent users = 10k threads → JVM dies

---

## Netty / Reactive Model

> Instead of blocking threads, Netty blocks nothing and waits for events

```
Client ──▶ Event Loop ──▶ Non-blocking IO ──▶ Callback
```

✔ Few threads
✔ No idle threads
✔ CPU stays busy

---

# PART 2️⃣ — What exactly is an Event Loop?

### Simple definition

> An event loop is a single-threaded loop that continuously:

1. Waits for events
2. Executes callbacks
3. Never blocks

---

## Event Loop Lifecycle (Netty)

```
while (true) {
    event = pollEvents();       // socket ready, data arrived
    handle(event);              // invoke handler
}
```

---

## Types of Events

Socket connection accepted
Data available to read
Write completed
Timer expired
Channel closed

# PART 3️⃣ — Netty Architecture (Deep Dive)

### Netty uses NIO (Non-Blocking IO)

Key concepts:

| Component      | Purpose                 |
| -------------- | ----------------------- |
| EventLoop      | Single-thread executor  |
| EventLoopGroup | Pool of EventLoops      |
| Channel        | Network connection      |
| Selector       | OS-level IO multiplexer |

---

## Thread Groups in Netty

### 1️⃣ Boss Group

Accepts incoming TCP connections

### 2️⃣ Worker Group

Handles read/write IO events

```
          Client
            │
            ▼
     ┌─────────────┐
     │ Boss Thread │
     └─────────────┘
            │ assigns
            ▼
     ┌──────────────────┐
     │ Worker EventLoop │
     └──────────────────┘
```

---

## Key Rule

> One Channel (connection) is always handled by the same EventLoop thread

This avoids locking 🔐

---

# PART 4️⃣ — Why NOT allocate one thread per request?

### ❌ Thread-per-request problems

| Issue             | Why            |
| ----------------- | -------------- |
| Context switching | CPU expensive  |
| Memory            | Thread stacks  |
| Idle waiting      | DB/API latency |
| Thread exhaustion | Leads to 503   |

---

### ✅ Event Loop advantages

| Advantage          | Explanation            |
| ------------------ | ---------------------- |
| Few threads        | ~CPU cores × 2         |
| No blocking        | Threads always working |
| Cache-friendly     | Less switching         |
| Linear scalability | Millions of sockets    |

---

## Example numbers

| Model  | Threads | Concurrent Requests |
| ------ | ------- | ------------------- |
| Tomcat | 200     | ~200                |
| Netty  | 8       | 100,000+            |

# PART 5️⃣ — How Spring WebFlux uses Netty Event Loop

```
Client → Netty → EventLoop → Router → Mono/Flux → EventLoop → Response
```

### Important Rule

> Never block the event loop

❌ BAD

```java
Thread.sleep(1000);
jdbcRepository.findAll(); // blocking
```

✅ GOOD

```java
return reactiveRepository.findAll();
```

---

## What if blocking is unavoidable?

### Offload to worker thread pool

```java
Mono.fromCallable(() -> blockingCall())
    .subscribeOn(Schedulers.boundedElastic());
```

📌 `boundedElastic` = controlled blocking threads

---

# PART 6️⃣ — Event Loop vs Thread Pool

| Feature    | Event Loop   | Thread Pool |
| ---------- | ------------ | ----------- |
| Threads    | Very few     | Many        |
| Blocking   | ❌ No         | ✅ Yes       |
| IO model   | Non-blocking | Blocking    |
| Scheduling | Cooperative  | Preemptive  |
| Best for   | IO-heavy     | CPU-heavy   |

---

# PART 7️⃣ — Event Loop timeline (one request)

```
t0: socket readable event
t1: event loop reads bytes
t2: decode HTTP
t3: invoke handler
t4: async DB call
t5: event loop moves on
t6: DB responds → event loop callback
t7: write response
```

⚠️ Event loop never waits

# PART 8️⃣ — Message vs Event (Distributed Systems)

This is VERY IMPORTANT conceptually.

---

## What is a Message?

> A message is a command or data sent from one service to another expecting processing.

### Characteristics

Has a destination
Often expects action
May require ack / response

### Examples

```json
{
  "type": "CREATE_ORDER",
  "orderId": "123"
}
```

📌 Kafka command topic
📌 RabbitMQ queue

---

### Message examples

PlaceOrder
ChargePayment
SendEmail
UpdateInventory

---

## What is an Event?

> An event represents a fact that already happened

### Characteristics

Immutable
No expectation of response
Broadcast in nature

### Examples

```json
{
  "event": "OrderPlaced",
  "orderId": "123",
  "timestamp": "..."
}
```

📌 Kafka topic
📌 Event stream

---

## Message vs Event Comparison

| Aspect     | Message        | Event         |
| ---------- | -------------- | ------------- |
| Intent     | Do this        | This happened |
| Coupling   | Tighter        | Loose         |
| Mutability | Can change     | Immutable     |
| Response   | Often expected | Never         |
| Retry      | Command retry  | Event replay  |

---

## Example Flow

### Command (Message)

```
Client → OrderService
         ↓
      Command: PlaceOrder
```

### Event

```
OrderService → Kafka
                ↓
          OrderPlaced Event
```

---

## Why this matters in Event Loop systems

Event loops process events
Kafka delivers events
Reactive pipelines respond to events
Non-blocking systems thrive on event-driven architecture

---

# PART 9️⃣ — One-liners for Interviews

✔ Netty avoids thread-per-request to eliminate blocking and context switching.
✔ Event loops multiplex many connections on few threads using non-blocking IO.
✔ Messages tell services what to do; events tell the system what already happened.
